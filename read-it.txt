     Context

     The organization (Rajdhani Yuva Sansad) already runs RYS Email Blaster — a
     Node/Express
     bulk-email tool that sends event invitations to participants from a CSV,
     via the Gmail API,
     with a 4-step wizard UI, per-account OAuth, a dual MySQL/Postgres data
     layer, and live
     streaming send-progress.

     They now want the same product for WhatsApp: identical UX and feature set,
     but the
     engine underneath changes because WhatsApp is a fundamentally different
     channel. The team
     previously tried mass-forwarding ~2000 messages by hand and got their
     number blocked.

     Route decision (already made, with the user): Build on Baileys
     (@whiskeysockets/baileys) — the free, open-source, unofficial WhatsApp Web
     protocol
     library. This is the only zero-cost route that can actually send to a list.
     It is
     directly analogous to how the email app swapped SMTP → Gmail API: a Node
     library, a
     persisted session (like the refresh token), promise-based send calls.

     The tradeoff — accepted knowingly — is ban risk to the sending number.
     Unlike the
     official Cloud API (which costs ~$8–24 per 2000 sends but is unbannable),
     Baileys drives a
     real WhatsApp session and can be flagged. We therefore make anti-ban pacing
     a first-class,
     configurable feature of the product, not an afterthought.

     Render

     limit
     editable, no hard ceiling.

     5. Data model

     Replace the email app's accounts table with wa_sessions. Baileys auth state
     = one
     creds object + many signal keys (pre-keys, sessions, sender-keys,
     app-state). We store:

     CREATE TABLE IF NOT EXISTS wa_sessions (
       id            VARCHAR(64) PRIMARY KEY,   -- slug of phone number, e.g. 
     "9188..."
       phone_number  VARCHAR(32)  NOT NULL UNIQUE, -- E.164 digits, no +
       display_name  VARCHAR(255) NOT NULL,      -- editable label ("Avni", "RYS
     Main")
       creds         TEXT NOT NULL,              -- JSON.stringify(Baileys 
     creds) w/ BufferJSON
       keys          TEXT NOT NULL DEFAULT '{}', -- JSON map of signal key-type 
     → {id: value}
       status        VARCHAR(24) NOT NULL DEFAULT 'disconnected', -- 
     connected|connecting|disconnected|logged_out
       created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
     );

     Baileys uses Buffers in creds/keys; serialize with Baileys' own
     BufferJSON.replacer /
     BufferJSON.reviver so bytes survive the round-trip. keys is written on
     nearly every
     message (signal ratchet advances) — that's expected; a single TEXT/JSONB
     blob is
     acceptable at this scale (a handful of numbers). init.js picks JSONB on PG,
     TEXT on
     MySQL.

     6. Baileys session & connection design (the new core)

     6a. DB-backed auth state — wa/authState.js

     Baileys ships useMultiFileAuthState(dir) which writes files to disk —
     useless on Render's
     ephemeral FS and awkward to manage. We implement a custom adapter:

     async function useDbAuthState(numberId) → { state: { creds, keys },
     saveCreds }
     - On load: read the wa_sessions row, revive creds and keys via
     BufferJSON.reviver.
     state.keys implements Baileys' SignalKeyStore interface: get(type, ids) and
     set(data) reading/writing the in-memory keys map, persisting to DB on set.
     - saveCreds() serializes creds back to the row.
     - New (unregistered) number: start from initAuthCreds(), persist after QR
     pairing.

     6b. ConnectionManager — wa/manager.js

     In-memory Map<numberId, { sock, status, qr }> — the live socket pool.
     - startConnection(numberId): build socket with
     makeWASocket({ auth: state, printQRInTerminal:false, browser: 
     Browsers.appropriate('RYS Blaster'), logger });
     wire connection.update (qr → store+emit; open → status connected, mark row;
     close →
     inspect DisconnectReason: reconnect unless loggedOut) and creds.update → 
     saveCreds.
     - getSocket(numberId): returns a connected socket or throws (send loop
     guards on this).
     - hydrateAll(): on server boot, load every wa_sessions row and reconnect in
     background
     so previously-added numbers come back online without re-scanning.
     - logout(numberId): sock.logout() + delete row (the "delete number"
     action).
     - Emits events (qr/status) consumed by the SSE endpoint.
